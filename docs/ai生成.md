实现 V2.5 引擎的脚本系统，包括 `script/parser.py`、`script/commands.py` 和 `script/executor.py`。

**脚本格式**（`.还没想好` 文件）：

**`parser.py`**：
- 读取 `.还没想好` 文件，逐行解析，返回 `List[Command]`。
- 支持行注释 `#`，空行跳过。
- 指令识别：`@scene`, `@bgm`, `@show`, `@hide`, `@choice`, `@label`, `@jump`, `@flag`, `@if` 以及对话文本。
- 对话文本格式：`"说话人，内容"` 或 `"内容"`（无名字直接显示），可选的 `[voice:文件名]` 标记。
- 解析 `@choice` 时生成 `ChoiceCommand` 包含选项列表和对应跳转。
- 错误处理：未知指令打印警告并跳过，文件不存在抛出异常。
- 使用 `abc` 抽象基类定义命令接口。

**`commands.py`**：
- 定义所有命令类，继承 `Command` 抽象类，实现 `execute(self, game) -> Generator` 方法（返回协程，可以为空生成器）。
- 每个命令的字段从解析结果注入。

**`executor.py`**：
- `ScriptExecutor` 接收 `Game` 引用，管理命令队列与当前协程。
- 核心方法：`run_script(script_name)`, `next()`, `update()`。
- 使用 `generator` 推进命令，每帧调用 `update()` 驱动当前命令。
- 对话命令会等待玩家点击，其他命令如背景切换自动连续执行（通过一个 `blocking` 属性标记）。
- 支持跳转：`jump(label)` 从标签处重新构造命令队列（需维护标签映射）。
- 分支实现：`ChoiceCommand` 暂停执行，显示选项 UI，玩家选择后根据跳转标签继续。
- 使用事件总线与 UI 交互（`game.dialog` 由 Game 注入，解耦）。

要求：
- 完整的错误恢复：脚本跳转缺失标签、无限循环防护（最大连续指令数）、文件加载失败时不能拖垮整个引擎。
- 变量系统：`@flag name true/false` 设置布尔变量，`@if name` 配合 `@jump` 条件跳转。
- 所有代码带类型注解，命令模式清晰，易于添加新指令（开闭原则）。

创作视觉小说的脚本是一个非常有趣但也需要严谨逻辑的过程，因为它不仅涉及传统的线性故事叙述，还需要处理玩家的选择和多重分支。

我们可以把这个庞大的工程拆解成几个核心模块来逐步构思。你可以参考以下框架来梳理你的灵感：

### 1. 确立核心概念 (Core Concept)
这是你整个故事的灵魂，决定了玩家为什么要玩这款游戏。
*   **一句话简介 (Logline)：** 尝试用一到两句话概括整个游戏的核心冲突。例如：“一个失去记忆的侦探必须在时间循环中找出校园连环谋杀案的真凶，否则他将在同一天死去。”
*   **核心情感/主题：** 你希望玩家通关后感受到什么？是救赎、绝望、甜蜜的恋爱，还是对人性的反思？

### 2. 构建世界观 (World-Building)
视觉小说非常依赖沉浸感，背景设定需要能够支撑你的故事。
*   **物理环境：** 故事发生在哪里？是现代都市、赛博朋克废土、中世纪奇幻大陆，还是一个封闭的密室？
*   **特殊规则：** 如果是架空世界或科幻/奇幻题材，这个世界有什么特殊的运行法则？（比如：魔法的代价、特定的社会等级、科技的限制等）。

### 3. 角色塑造 (Character Design)
视觉小说的核心卖点往往是角色。
*   **主角 (主角/POV)：** 玩家的代入点。TA的初始目标是什么？TA有什么致命的弱点或过去的阴影？
*   **主要配角/可攻略角色：** 
    *   给每个核心角色设定一个**表层性格**（傲娇、阳光、冷漠）和一个**深层动机**（复仇、渴望被爱、隐藏秘密）。
    *   确保每个角色都有自己独立的故事弧光，而不是纯粹为了推动主角剧情而存在。

### 4. 剧情结构与分支设计 (Plot & Branching)
这是视觉小说脚本与传统小说最大的区别。
*   **共通线 (Common Route)：** 游戏的开篇部分。主要任务是介绍世界观、让核心角色悉数登场，并抛出主线悬念，建立玩家与角色之间的初步羁绊。
*   **分歧点 (Choices/Flags)：** 玩家在共通线中做出的选择，将决定剧情走向。建议早期设计一些影响好感度的小选择，中后期设计决定生死或路线的重大选择。
*   **个人线/结局 (Routes & Endings)：** 
    *   **Good Ending (GE) / True Ending (TE)：** 揭开所有谜团或完成角色救赎。
    *   **Bad Ending (BE)：** 选错导致的死亡或悲惨结局。高质量的 BE 往往能极大提升剧情的厚度。
    *   **Normal Ending (NE)：** 平淡收场。

### 5. 剧本落地格式 (Scripting Format)
当你开始动笔写具体台词时，可以采用类似这样的格式，方便后续导入游戏引擎（如 Ren'Py, Krkr 等）：
> **场景：** 教室，白天
> **BGM：** 轻松的日常音乐
> **立绘：** [角色A_微笑]
> **角色A：** “早上好！今天你也迟到了呢。”
> **玩家选择：** 
> 选项1：“因为昨天熬夜打游戏了。”（角色A好感度+1）
> 选项2：“要你管。”（角色A好感度-1）

1. 极简的“剧本式”语法 (DSL 设计)
视觉小说脚本的创作者往往不仅是程序员，更是编剧。脚本语言需要像写常规剧本一样直观，剥离掉多余的括号和符号，只保留核心的叙事流。

我会倾向于采用类似下面这种高可读性的格式，引擎端再将其解析为 JSON 或抽象语法树（AST）：

// 场景与资源初始化
@scene bg="classroom_day.png" bgm="sunny_morning.mp3" transition="fade"

// 角色登场与状态
@show character="Aline" pose="smile" position="center"

Aline:
"早上好！今天怎么来得这么早？"

Player:
"为了提前来复习功课。"

// 变量控制与分支逻辑
@if logic="player_study_stats > 50"
    Aline (surprised):
    "哇，你最近真的很用功呢！"
@else
    Aline (teasing):
    "平时上课都在睡觉的人，这话可一点说服力都没有哦。"
@endif

// 选项交互
@choice prompt="你的回答："
    => "毕竟快考试了。" 
        @set player_study_stats += 5
        @jump target="scene_study_hard"
    => "其实是定错闹钟了。"
        @set Aline_affection += 2
        @jump target="scene_funny_chat"


2. 状态机与持久化数据管理
在编写大型视觉小说时，状态管理是重中之重。我会将脚本的逻辑层划分为两类：

全局状态 (Global State)： 跨越周目的数据，例如真结局的解锁进度、CG 画廊的收集度。

局部状态 (Local State)： 当前周目的好感度、关键物品的获取（Flags）。

在脚本编写中，我会建立一套严格的命名规范，例如使用 G_ 前缀代表全局变量，L_ 代表当前线路变量，确保在复杂的网状叙事中不会出现逻辑死结。

3. 高级系统的接口预留 (Action Hooks)
考虑到现代引擎的扩展性，纯文本和静态图片有时是不够的。在编写脚本时，我会频繁使用类似“钩子（Hooks）”或“动作调用（Action calls）”的指令。

例如，如果你的引擎未来需要接入更复杂的动态系统（比如处理环境模拟，甚至是接入一些动态的智能逻辑、NPC 的行为决策树等），脚本需要能够轻松调用外部工具或执行特定技能：

// 调用引擎底层注册的特定“工具”或“技能”
@call_system tool="weather_simulator" params={"temperature": 25, "humidity": "high"}
@call_action action="camera_shake" intensity="heavy" duration="2s"

这种设计可以将“演出效果”和“底层逻辑”从文本脚本中解耦，让脚本专注于“发生了什么”，而让引擎底层专注于“怎么实现”。




这种脚本语言我们可以将其命名为 **W-Script (Wilson Script)**。它是专门为**高性能、流式解析、低内存占用**的视觉小说引擎设计的。

为了适配你 **v2.5 引擎的惰性读取（Lazy Loading）**特性，这种语言不再将脚本看作“纯文本”，而是将其看作一串**带有地址索引的操作指令流**。

以下是该语言的四个核心维度详细介绍：

---

### 一、 语法结构：基于“前缀触发”的解析逻辑
在惰性读取架构下，解析器（Parser）最怕复杂的上下文关联。W-Script 采用**行首字符识别法**，让引擎在读取到每一行字节时，瞬间决定分发逻辑。

| 符号 | 定义 | 示例 | 引擎行为 |
| :--- | :--- | :--- | :--- |
| `##` | **全局锚点** | `## [Chapter_1]` | 建立物理偏移量索引，支持秒转跳 |
| `::` | **局部标记** | `::Sub_Talk` | 供内部跳转或函数式调用使用 |
| `@` | **原子指令** | `@bg name="city"` | 触发底层渲染器或音频管理器 |
| `[]` | **状态声明** | `[Aline:blush]` | 快速切换立绘/Slot状态，不阻塞对白 |
| `"` | **对话流** | `"你好。"` | 进入打字机队列，挂起解析器等待点击 |
| `//` | **注释** | `// 这里是逻辑` | 惰性读取时直接跳过，不占用计算资源 |

---

### 二、 逻辑控制：基于“堆栈”与“偏移”的跳转
传统的脚本跳转需要搜索字符串，这在惰性读取大文件时会导致明显的掉帧。W-Script 引入了**二进制辅助索引**。

1.  **静态偏移索引 (Offset Table)**：
    当引擎首次加载 `.gal` 文件时，会极速扫描所有的 `##` 和 `::`，并记录下它们在文件中的 **Byte Position（字节位置）**。
    *   *优势*：当执行 `@jump` 时，引擎直接调用 `fseek(pos)`，无论文件多大，跳转延迟恒定为 0。

2.  **函数式调用 (@call & @return)**：
    支持像写代码一样写剧本。
    *   当 `@call ::Morning_Routine` 被触发，引擎将当前行的字节地址压入**执行堆栈（Stack）**。
    *   执行完子模块遇到 `@return`，堆栈弹出地址，指针瞬间跳回原点。

---

### 三、 资源调度：槽位（Slot）与预判加载系统
为了解决“边读边播”可能产生的资源卡顿，W-Script 强制采用**槽位管理**。

*   **槽位抽象**：引擎预设 `bg`, `mid_center`, `mid_left`, `mid_right`, `fg` 等槽位。脚本作者不需要管理“Image对象”，只需要操作“槽位内容”。
*   **指令示例**：
    ```text
    @show Aline slot=mid_left transition=dissolve
    ```
*   **预读缓冲区 (Prefetch Buffer)**：
    由于是惰性读取，引擎会维护一个“向前视野”。当解析器处理第 100 行时，IO 线程会自动静默扫描第 101-120 行。如果发现 `@show` 指令，会提前将图片载入 GPU 显存。

---

### 四、 数据驱动：响应式文本与状态快照
W-Script 允许剧本在**不重新编译**的情况下，实现动态内容。

1.  **内联表达式 (Inline Expression)**：
    利用 `${}` 语法，在文本渲染的最后一毫秒进行插值。
    ```text
    "现在的温度是 ${Env.temp} 度，你的心情是 ${Player.mood}。"
    ```
2.  **原子化存档 (Atomic Checkpoints)**：
    在惰性读取中，存档不记录“执行到了哪行字”，而是记录：
    *   **File_Pointer**: 当前解析到的字节位置。
    *   **Stack_Depth**: 当前 `@call` 的嵌套深度。
    *   **Variable_Delta**: 自上次进入该场景后变化的变量。

---
